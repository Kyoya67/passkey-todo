## SameSiteとCSRFの脅威モデルの検討

- **使用箇所**：`backend/internal/middleware/csrf.go`、`DESIGN.md`、PRの設計説明
- **AIの利用内容**：Cookieの自動送信と読み取りの違い、SameSite（Strict/Lax/None）、OriginとSiteの違いを解説し、攻撃成立条件を整理した。
- **採用理由**：`SameSite=Strict`でも、`https://evil.kyo8.dev`と`https://api.ca-techlounge-todo.kyo8.dev`は同じschemeful site（`https://kyo8.dev`）になり得る。同一Siteの別OriginからのリクエストにCookieが添付される条件があるため、状態変更APIで正規フロントエンドのOriginだけをサーバー側で許可する多層防御を採用した。ただし、攻撃成立には被害者のセッション、リクエスト形式、ブラウザのCORS/preflight挙動等も関係し、現時点のアプリで具体的なCSRF攻撃の成功を確認したわけではない。
- **開発者による対応**：ユーザーは`kyo8.dev`を自分で管理しており、他サブドメインで悪意あるコードを意図的に公開する予定はないと説明。それでも将来のサブドメイン追加・侵害・設定変更に備え、Origin制約を追加する判断を依頼。変更コードの採用・マージ判断は未実施。
- **検証方法**：既存のCookie設定、Origin検証、WebAuthnの認証経路をコードから確認。脅威モデルの整理であり、攻撃再現テストは未実施。
- **代表的なプロンプト**：「でもkyo8.devの所有者は僕だから僕が悪意あるコード書かなければいいだけ？でも一応対応しておいて」「CORSとCSRFってどう違うんだっけ」「一般的なCSRF攻撃って成立しなくない？」「sameSiteの設定をしなければ、全く別のドメインからでもクッキーを送信できちゃうってこと？」

## CORSとCSRF許可Originの分離

- **使用箇所**：`backend/internal/config/config.go`、`backend/cmd/api/main.go`、`compose.yaml`、`.env.example`、`infra/aws.tf`、`infra/modules/ecs/`、`api/openapi/openapi.yaml`
- **AIの利用内容**：`CSRF_ALLOWED_ORIGINS`を独立設定として導入し、TODOの状態変更を専用許可リストの完全一致で検証。未許可・欠落Originを403にする。OpenAPIに403レスポンスを追記。
- **採用理由**：ローカルSwagger UI (`http://localhost:8081`) からAWSの公開読み取りAPIを確認するためCORSには残しつつ、本番のCSRF許可対象は正規フロントエンドのみに限定する。localhostのOriginが許可されても第三者にセッションCookieが渡るわけではないが、不要な信頼範囲は増やさない。
- **開発者による対応**：ユーザーはlocalhostのCORS許可がSwagger UIによるクラウドAPIの確認目的だったと説明。Swagger UIで認証付き操作を行えない現状と、CookieのSameSite=Strictを維持することを確認。レビュー・マージ判断は未実施。
- **検証方法**：構成と設定の静的確認に加え、後続作業で`go test ./... -coverprofile=... -count=1`と`go vet ./...`をローカル実Go依存で実行した。GitHub ActionsはOrganizationの請求・利用制限によってジョブ開始不可。ブラウザE2Eは未実施。
- **代表的なプロンプト**：「ローカルで立ち上げたswagger上でクラウドのapi確認するために許可した」「そこもじゃあ修正しておいてくれ。てかswaggerまた使わなくなってるな」
