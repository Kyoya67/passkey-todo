## パスキー登録・ログイン

- 使用箇所：`backend/internal/auth/`、`api/openapi/openapi.yaml`、`backend/db/migration/002_create_passkey_accounts.up.sql`
- AIの利用内容：WebAuthnライブラリを使った登録・ログイン、チャレンジの使い捨て、ユーザーとCredentialの保存、異常系テストを実装した
- 採用理由：パスキーの署名検証を独自実装せず、API内の認証処理として扱うため
- 開発者による対応：CognitoをやめてGo API内で実装する方針を指定し、Handler・Service・Repositoryの責務とファイル構成を対話で見直した。ログイン時のHTTP 400はNetworkタブと診断ログで切り分けた
- 検証方法：ローカルで登録・ログインを操作し、`go test ./...`を実行した
- 代表的なプロンプト：「それぞれの責務を考えた上でhandlerとserviceも作っちゃって」「エラーハンドリングが雑だからそこ修正しておいて特定しよう」

## セッションとユーザー別TODO

- 使用箇所：`backend/internal/middleware/auth.go`、`backend/internal/todo/`、`backend/db/migration/003_assign_todo_owner.up.sql`、`backend/db/migration/004_require_todo_owner.up.sql`、`frontend/`
- AIの利用内容：RedisセッションによるTODO APIの認証、所有者IDを条件とするCRUD、ログアウト、フロントエンドの認証画面とテストを実装した
- 採用理由：クライアントが送るユーザーIDを信用せず、サーバー側セッションから所有者を決めるため
- 開発者による対応：チャレンジとセッションの保存先をRedisにすること、ログアウト導線、`todos.user_id`のNOT NULL化を指定した。所有者未設定の既存行は自動削除・自動割り当てしない方針にした
- 検証方法：ローカルDBでマイグレーション004を適用し、TODOの`user_id`がNOT NULLであることを確認した。TODO Repositoryの統合テスト、`go test ./...`、`sqlc vet`を実行した
- 代表的なプロンプト：「ログイン時のチャレンジやセッションもredis使う予定だからやはりチャレンジはredisにしよう」「エラーハンドリングについては後回し。次はログインに成功したユーザーのみtodo使えるようにしたい」「`todos.user_id`は既存TODOを所有者未設定のまま保持するためNULLを許容する これもうユーザーありだから修正できない？NULL禁止にしたい」

## ローカル・AWS構成と設計文書

- 使用箇所：`compose.yaml`、`infra/modules/elasticache/`、`infra/modules/ecs/`、`DESIGN.md`、`backend/TESTING.md`
- AIの利用内容：ローカルRedisとElastiCacheの接続設定、ECSタスク定義への環境変数追加、ER図・認証シーケンス図・CD条件の文書化を支援した
- 採用理由：認証ロジックを共通にし、環境ごとの接続先と保存データを分離するため
- 開発者による対応：ローカルとAWSで同じアプリケーションコードを使う方針を確認し、DESIGN.mdにはテーブルの役割、認証フロー、CDの条件を簡潔に記載するよう依頼した
- 検証方法：`docker compose config --quiet`、`sqlc diff`、`git diff --check`を実行した。AWSでの認証・TODOのE2E検証は未実施
- 代表的なプロンプト：「ローカルと本番の差分をなくしたいんだけどcompose.yamlのredisとクラウド上のredisって同じ設定使えるようになってる？」「パスキー認証の仕組みについてmermaidでシーケンスで書いて。それとデータベース設計でそれぞれのテーブルの役割を簡潔に」
