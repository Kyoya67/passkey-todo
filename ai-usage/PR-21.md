# AI利用記録：PR #21

## 利用モデル・ツール

- ツール：OpenAI Codex
- 利用目的：Issue #5のテスト方針、Fakeによる層別テスト、カバレッジ計測、テスト方針ドキュメントの整理
- 最終的な要件解釈、採用判断、コード確認、検証は開発者が行う

## Handler・Serviceのテスト

- 使用箇所：`backend/internal/handler/todo_test.go`、`backend/internal/service/todo_test.go`
- AIの利用内容：HandlerではFake Service、ServiceではFake Repositoryへ依存を差し替え、HTTPステータス、入力検証、業務ルール、エラー変換をテストする方針を相談した
- 採用理由：外部DBや実際のHTTPサーバーに依存せず、各層の責務を個別に検証するため
- 開発者による対応：正常系だけでなく、空タイトル、不正JSON、不正ページネーション、サービスエラー、存在しないTODOの404をテストした
- 検証方法：`go test ./...`、パッケージ別カバレッジ計測、`go vet ./...`を実行した
- 代表的なプロンプト：
  - 「既存のHandlerとServiceのinterfaceを使い、Fakeへ差し替えて、HTTPステータス・入力検証・エラー変換を検証するGoテストの観点を整理して」
  - 「正常系だけでなく、HandlerとServiceで優先すべき異常系テストを、課題のTODO API要件に対応させて整理して」

## Repositoryのテストと依存性分離

- 使用箇所：`backend/internal/repository/todo.go`、`backend/internal/repository/todo_test.go`
- AIの利用内容：`*sqlc.Queries`へ直接依存していたRepositoryを、sqlcのクエリメソッドを持つinterfaceへ差し替え、Fakeで引数・戻り値・エラー伝播を検証する方針を相談した
- 採用理由：生成コードを直接編集せず、Repositoryがsqlcへ渡すSQLパラメータと結果処理をテスト可能にするため
- 開発者による対応：`todoQueries` interfaceをRepositoryパッケージ内に定義し、Create、List、Update、Deleteの引数と結果、DBエラーの伝播をテストした。生成されたsqlcコード自体のテストは追加していない
- 検証方法：`go test ./internal/repository`、`go tool cover -func=coverage.out`を実行した
- 代表的なプロンプト：
  - 「sqlcが生成した`*Queries`をRepositoryが直接持つ構成で、生成コードをテスト対象にせずRepositoryのSQL引数とエラー処理をFakeで検証するには、どのinterfaceを定義すべきか」

## テスト方針とカバレッジ記録

- 使用箇所：`backend/TESTING.md`、`DESIGN.md`
- AIの利用内容：責務単位のテスト観点、関数別カバレッジ、全体カバレッジ、生成コードをカバレッジ評価から分けて記録する方法を整理した
- 採用理由：テスト対象と未対象の範囲を明確にし、実施したカバレッジ結果だけをドキュメントに記録するため
- 開発者による対応：Handler 93.2%、Service 90.0%、Repository 100.0%、全パッケージ29.3%を`backend/TESTING.md`へ記録した。`coverage.out`は生成物としてGit管理対象外にした
- 検証方法：`go test ./... -coverprofile=coverage.out`、`go tool cover -func=coverage.out`、`go vet ./...`を実行した
- 代表的なプロンプト：
  - 「Goの責務別テスト方針とカバレッジ結果をドキュメント化する場合、Handler・Service・Repositoryの観点と、生成コードや外部I/Oをどう扱うべきか整理して」
