# AI利用記録：PR #19

## 利用モデル・ツール

- ツール：OpenAI Codex
- 利用目的：OpenAPI仕様、コード生成、Swagger UI、CORSの設計と実装支援
- 最終的な要件解釈、採用判断、コード確認、検証は開発者が行う

## OpenAPI・oapi-codegen

- 使用箇所：`api/openapi/openapi.yaml`、`backend/internal/openapi/oapi-codegen.yaml`、`backend/internal/openapi/api.gen.go`、`backend/internal/handler/todo.go`、`backend/internal/router/router.go`
- AIの利用内容：OpenAPIをAPI仕様の正とするSpec-first方針、`oapi-codegen`によるGoコード生成、生成されたEcho Server Interfaceの利用方法を相談した
- 採用理由：OpenAPIと実装の不整合を減らし、リクエスト・レスポンス型、Server Interface、ルーティング登録を仕様から生成するため
- 開発者による対応：生成コードの内容を確認し、既存Handlerを生成されたServer Interfaceに適合させ、手動ルーティングを生成ルート登録へ変更した
- 検証方法：`oapi-codegen`、`go mod tidy`、`go test ./...`、`go vet ./...`を実行した
- 代表的なプロンプト：
  - 「OpenAPIをAPI仕様の正とするSpec-first開発では、openapi.yamlからGo/Echoの型・Server Interface・ルーティングを生成する構成をどう設計するか。既存のHandler、Service、Repositoryとの責務分担も含めて説明して」
  - 「既存のEcho HandlerをOpenAPIから生成したServer Interfaceへ適合させる場合、手動ルーティングと生成ルーティングの違い、変更箇所、注意点を整理して」
  - 「OpenAPI定義をバックエンド配下ではなくモノレポのapiディレクトリで共有する場合の利点と、oapi-codegen設定をバックエンド側に置く理由を比較して」

## Swagger UI・CORS

- 使用箇所：`compose.yaml`、`.env.example`、`backend/internal/config/config.go`、`backend/internal/middleware/cors.go`、`backend/cmd/api/main.go`
- AIの利用内容：ローカルSwagger UIの起動方法、API環境の切り替え、Swagger UIとバックエンド間のCORS、クラウド配置方針を相談した
- 採用理由：ローカルレビュー時にOpenAPIを確認し、Swagger UIからバックエンドAPIを実行できるようにするため
- 開発者による対応：Swagger UIをComposeの開発用サービスとして追加し、許可Originを環境変数で設定するCORSミドルウェアを実装した
- 検証方法：`docker compose config`、`go mod tidy`、`go test ./...`、`go vet ./...`を実行した
- 代表的なプロンプト：
  - 「Swagger UIをローカルComposeだけで運用し、クラウドのバックエンドとは分離する構成と、Swagger UIをECSや静的ホスティングへ配置する構成を、コスト・運用・セキュリティ・レビューのしやすさで比較して」
  - 「Swagger UIをlocalhost:8081、バックエンドAPIをlocalhost:8080で起動する場合にCORSが必要になる理由と、将来のフロントエンド開発サーバーにも対応できる許可Originの管理方法を設計して」
  - 「CORSをIssue #3のOpenAPI・Swagger UI対応に含めるべきか、別Issueへ分けるべきか。変更の依存関係と責務の観点から判断して」
