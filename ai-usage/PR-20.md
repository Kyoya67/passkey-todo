# AI利用記録：PR #20

## 利用モデル・ツール

- ツール：OpenAI Codex
- 利用目的：Issue #4のDockerfile、Docker Compose、コンテナ間通信、起動確認の実装方針確認と検証内容の整理
- 最終的な要件解釈、採用判断、コード確認、検証は開発者が行う

## Dockerfileの構成

- 使用箇所：`backend/Dockerfile`、`backend/.dockerignore`
- AIの利用内容：ローカルとAWSで同じDockerfileを利用する方針、マルチステージビルド、Goのビルド環境と実行環境の分離について相談した
- 採用理由：ビルド用ツールを実行イメージへ含めず、ローカルとAWSで同じバックエンド用コンテナイメージを利用するため
- 開発者による対応：`golang:1.25-bookworm`でLinux向けバイナリをビルドし、`debian:bookworm-slim`へコピーする構成を採用した。`ca-certificates`はTLS接続先の証明書検証に使うCA証明書一覧であり、サーバー証明書を発行するものではないことを確認した
- 検証方法：`docker compose build backend`でイメージをビルドした
- 代表的なプロンプト：
  - 「ローカルとAWSの両方で利用するDockerfileを一つにする場合、DockerfileとComposeの責務をどう分けるべきか。Goのマルチステージビルドも含めて整理して」
  - 「Dockerfileの実行イメージにca-certificatesをインストールする目的は何か。ACMのサーバー証明書との違いと、PostgreSQL接続への関係を説明して」

## Docker Composeの構成

- 使用箇所：`compose.yaml`、`.env.example`、`DESIGN.md`、`README.md`
- AIの利用内容：バックエンド、PostgreSQL、Swagger UIを別コンテナとして起動する構成、環境変数の受け渡し、Composeネットワーク上のサービス名によるDB接続について相談した
- 採用理由：サービスごとの責務を分離し、ローカルレビュー時に同じ起動手順で必要なサービスを立ち上げるため
- 開発者による対応：`backend`サービスを追加し、`DB_HOST=db`、PostgreSQLの認証情報、CORS設定を明示的に渡す構成にした。ホスト公開ポートは`BACKEND_PORT`、コンテナ内部ポートは`BACKEND_CONTAINER_PORT`で設定し、Goアプリ、Dockerfile、Composeで同じ内部ポートを使うようにした
- 検証方法：`docker compose config`、`docker compose up -d`、`docker compose ps`、`docker compose logs --no-color backend`を実行した
- 代表的なプロンプト：
  - 「ComposeでバックエンドとPostgreSQLを別コンテナとして起動する場合、ホスト側のDB接続設定とコンテナ間のDB接続設定はどう分けるべきか」
  - 「ローカル用Composeの設定をAWS ECSでも利用する場合、Dockerfileと環境変数のどこを共通化し、どこを環境ごとに分けるべきか」
  - 「Dockerfileの`EXPOSE`、Composeの`ports`、Goアプリの待受ポートを環境変数で統一する場合の実装方法と、`ARG`と実行時環境変数の違いを説明して」

## PostgreSQLのhealthcheck

- 使用箇所：`compose.yaml`の`db.healthcheck`、`backend.depends_on`
- AIの利用内容：`pg_isready`、`service_healthy`、`depends_on`の関係を確認した
- 採用理由：PostgreSQLコンテナの起動完了前にバックエンドが接続して終了する可能性を減らすため
- 開発者による対応：`pg_isready -U $${POSTGRES_USER} -d $${POSTGRES_DB}`をhealthcheckに設定し、`condition: service_healthy`でPostgreSQLのhealthcheck成功後にバックエンドを起動する構成にした
- 検証方法：`docker compose ps`で`db`が`healthy`、`backend`が起動中であることを確認した
- 代表的なプロンプト：
  - 「`healthcheck.test`の`pg_isready`と`depends_on.condition: service_healthy`は、Compose内部でどのように関連付けられるか」
  - 「`service_healthy`はDocker Composeの予約語か。`condition`で指定できる値と、それぞれの用途を説明して」

## PostgreSQLのTLS方針

- 使用箇所：`backend/internal/database/database.go`の`sslmode=disable`、後続Issue #7
- AIの利用内容：PostgreSQL側の`ssl`設定、アプリ側の`sslmode`、`ca-certificates`の役割を整理し、ローカル環境とAWS RDS環境のTLS方針を相談した
- 採用理由：Issue #4ではローカルPostgreSQLのTLS証明書管理まで扱わず、AWS RDS構築時にDB側とアプリ側のTLS設定を合わせる方針とするため
- 開発者による対応：ローカルのPostgreSQLで`SHOW ssl`が`off`、アプリ側が`sslmode=disable`であることを確認した。RDSのTLS有効化、適切な`sslmode`、CA証明書検証、Secrets管理をIssue #7の完了条件へ追記した
- 検証方法：`docker compose exec -T db psql -U todo -d todo -Atc 'SHOW ssl;'`を実行し、`off`を確認した。RDS接続とAWS上のTLS検証は実施していない
- 代表的なプロンプト：
  - 「PostgreSQL側でTLSを有効にしても、アプリ側の`sslmode`が無効ならどうなるか。ローカルPostgreSQLとAWS RDSでの設定方針を分けて説明して」

## コンテナ上のAPI動作確認

- 使用箇所：Composeで起動したバックエンドのHTTPエンドポイント
- AIの利用内容：コンテナ起動後に課題の必須API 4本を確認する手順を整理した
- 採用理由：Issue #4の完了条件であるコンテナ環境のTODO API動作を確認するため
- 開発者による対応：検証用TODOを作成し、一覧取得、更新、削除を実行した。検証用データは削除した
- 検証方法：`go test ./...`、`go vet ./...`、`docker compose config`、`docker compose build backend`、`docker compose up -d`を実行した。Health APIはHTTP 200、TODO APIは作成`204`、一覧取得`200`、更新`204`、削除`204`を確認した
- 代表的なプロンプト：
  - 「Docker Composeで起動したバックエンドに対して、healthとTODOの作成・一覧取得・更新・削除を確認する最小限のHTTP検証手順を整理して」
